# 自动化系统架构和每日日程

## 指挥层

负责人（唯一定价/支付/版权/上线审批者）→ AI 产品总监（汇总目标、排优先级、生成任务）→ GitHub Issues（真任务队列）→ AI 研发执行器（在独立分支产出 PR）→ CI 自动测试（静态、单元、跨平台、视觉抽查）→ 人工抽验与授权合并 → 发布候选版 → 数据反馈。

**注意**：此仓库当前只完成日报、基础单测和网页游戏原型。AI 研发执行器、自动 PR 与真实生产数据接入属于下一阶段实施，不要混淆。

## 八种角色的具体交付

1. 策略/市场：竞品趋势、用户需求和可验证假设（附来源与时间）。
2. 游戏主策：唯一核心乐趣、GDD、数值测试、可玩性验收。
3. 叙事/美术：角色设计系统、色彩与原创素材权属台账。
4. 客户端研发：独立分支上开发、小 PR、单元测试。
5. QA：回归脚本、兼容性、性能和阻断缺陷。
6. 增长发行：商店页、创作者名单、活动计划、内容 A/B 测试。
7. 数据运营：留存漏斗、营销成效、反馈分类、异常告警。
8. 财务合规：成本预测、游戏著作权、使用条款、隐私和平台规则。

## 每日工作节拍

- 08:00：读取任务队列、上一日指标，生成今日唯一核心任务。
- 09:00–12:00：研发执行器在隔离分支开发功能、单元测试及文档。
- 13:00：CI 回归、错误修复、生成可玩候选包。
- 15:00：运营系统分析玩家反馈，提交改进建议，更新内容计划。
- 18:00：记录日报：已完成/证据/失败原因/用时与成本/第二天任务。
- 人类每天只需集中审批、提供真实玩家体验判断和关键创意选择。

这里的时间节拍是**目标运营流程**，不是本示例已经部署的执行频率。示例 Actions 仅执行每日任务报告和 CI，不执行自动 coding、外部营销或付费上架。

## 三道质量门

1. 代码门：测试通过、无明显安全漏洞、不可写密钥到仓库。
2. 体验门：真实试玩、崩溃率和缺陷、基本性能达标。
3. 商业门：验证定位、转化和玩家反馈，合规审核完成再发布。

## 游戏运营禁区

- 未成年人保护、隐私合规、素材侵权和 AI 内容披露必须主动审查。
- 国内商业运营应按具体产品/渠道核对版号、网络游戏出版和平台所需手续，不能以“只是小游戏”推定无需审批。
- 用分阶段止损的研发策略控制风险；不从最乐观投产率推导营收。
